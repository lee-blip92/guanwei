# 多平台评论采集 Implementation Plan

**Goal:** 在一个产品研究任务中多选 MediaCrawler 当前支持的七个平台，串行采集、统一核查和分析，并保持来源与任务状态可追溯。

**Architecture:** 平台注册表维护 ID、名称与实际排序能力。每个平台独立采集子进程，任务内串行执行并持久化分平台状态。统一数据边界隔离上游字段，SQLite 笔记改用任务＋平台＋笔记 ID，评论继续按平台＋评论 ID 去重。

**Tech Stack:** 沿用 React/TypeScript、FastAPI、SQLite、MediaCrawler 独立适配层。

## ADR 与取舍

- 采用每平台独立子进程，复用现有单采集锁，避免共享全局 config 和浏览器冲突。前端允许任意非空平台子集，默认仅小红书，旧任务兼容。
- 采集上限按每个平台分别计算，界面明确展示选择数量与合计上限，避免前几个平台耗尽全局预算而后面完全不采。
- 保留小红书已验证桥接器，为其余平台使用统一有界搜索/评论循环，复用上游客户端和浏览器启动。支持平台各自实际能力；不提供虚假的日期筛选，跨平台排序只显示共同能力。
- 平台故障记录为失败并继续后续平台；登录/验证暂停当前平台，用户恢复后继续；取消停止剩余平台；有可用数据则生成部分完成报告。
- 跨平台 ID、父评论和笔记上下文必须按平台隔离；报告展示平台样本分布，不将平台样本数理解为用户数。

## 实施与验收

1. `platforms.py`：登记 xhs/dy/ks/bili/wb/tieba/zhihu；TaskConfig 增加 platforms，校验非空、去重、支持排序。
2. 数据迁移：notes 复合主键、raw_records 平台列、platform_runs；保留旧 xhs 数据和报告。测试相同 ID 的跨平台隔离与迁移。
3. 多平台规范化：原生 API/MediaCrawler 导出字段映射；明确平台时可导入 JSON/JSONL/Excel；多选但无平台标识时拒绝猜测。
4. 采集：平台独立目录/配置/取消恢复标记，六个平台独立 API 分支，平台级失败续跑和实际计数。
5. 前端：平台多选、全选、能力提示、分平台运行状态、评论平台筛选、报告来源和分布。
6. 检查：七个平台有界客户端协议替身测试、多平台任务编排/登录恢复/部分失败/取消、平台去重与父关系、导出一致性；构建与浏览器核查。真实平台登录只能由用户人工完成，未实采的平台必须明确验证边界。
7. 更新采集说明、架构与验收记录，保留非商业学习许可证。无需新增队列、微服务或账号体系。
